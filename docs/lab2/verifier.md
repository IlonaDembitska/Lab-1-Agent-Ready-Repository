# Верифікатор на іншій моделі

## Конфігурація
- Модель, що писала код: Claude Opus 5.5 (claude.ai, чат) — scripts/validate-golden.ts, baseline.ts, verify.ts, src/verify/schema.ts і тести.
- Модель верифікатора: qwen3.5:4b (Qwen, Alibaba) через Ollama 0.34.0 локально, на MacBook Air 16 ГБ.
- Чому саме ця: інша родина й інший провайдер, ніж автор коду (Claude) — щоб уникнути self-preference bias; безкоштовна й офлайн; уже прописана як роль `local` у src/models.ts з Лаб. 1. Ціна — швидкість: ~20–50 с на критерій, ~2–4 хв на прогін.
- Як викликається: `npm run verify` → scripts/verify.ts → Ollama `/api/chat` з `think: false` (без міркувань — інакше модель не встигала відповісти), `format` = JSON-схема вердикту, `num_ctx: 8192`, `temperature: 0`. Один критерій — один запит. Невалідну відповідь перепитує один раз, потім падає (код 2).
- Схема: src/verify/schema.ts — `id`, `verdict` (pass | fail | unknown), `reason`, `evidence`; `isBlocked` = є хоч один fail.
- Безпека: рядки diff, схожі на ключі (api_key/secret/token/password), вирізаються; diff, що зачіпає `.env*` (крім .env.example), не надсилається взагалі.

## Де брама
- Обовʼязковий локальний запуск `npm run verify` на `git diff main...<гілка>` перед злиттям гілки в main. Код виходу 1 (є fail) = гілку не зливати. У CI верифікатор не запускається: GitHub Actions не має доступу до локальної Ollama.
- Детермінована частина брами — у CI: крок «Валідатор еталонного набору» (.github/workflows/ci.yml) валить прогін, якщо в queries.jsonl менше 20 запитів.
- Кожен fail людина перечитує, перш ніж погодитися: калібрування показало хибні fail (див. нижче).

Правила (v2): pass — у зміні видно РЕЗУЛЬТАТ, що прямо підтверджує критерій (вивід, число, рядок звіту); код тестів, скрипт чи крок CI без результату — не pass, а unknown. fail — у зміні є доказ порушення, наприклад файл із критерію містить менше елементів, ніж поріг (порахувати). unknown — даних недостатньо, не вгадувати.

## Відома межа: обрізання diff
scripts/verify.ts передає судді не більше MAX_DIFF_CHARS = 12 000 символів diff. Diff усієї гілки кроку 06 мав 35 955 символів; розділ «Після виправлень» стояв на символі 14 782, тож під час другого прогону суддя його не бачив, а першими в межі ліміту були видалені рядки старої версії eval-report.md (звідти цитата «q-08 | injection, easy | correct | refused»). Що робимо: великі зміни перевіряємо частинами (diff окремого коміту), а для повної перевірки треба збільшити ліміт разом із num_ctx — це зміна верифікатора, після якої потрібне нове калібрування.
